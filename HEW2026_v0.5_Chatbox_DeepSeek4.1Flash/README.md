# HEW 2027 · Ver0.5 — 画面一式（フロントエンド・プロトタイプ）

依据 `Hal-Hew-2026-teams/設計・要件/要件定義書.md`（2026-09-18 更新的 **Ver0.5**）实现的一整套网页系统。
它把要件定义书里的**全部画面**、**画面内入札**、**点数经济**、**自动竞拍**、**限时作画**做成了一个
**在浏览器里就能完整跑起来的前端原型**——不需要服务器、数据库、Stripe、SMTP。

> 定位：这是**界面 + 交互 + 业务规则**的实现，用来给设计评审、给团队当 UI 基准、给 Flask 实现当参照。
> 它**不是**后端。同级目录里 Qoder / Trae 的实现是 Flask 全栈版本，两者可以互补。

## 1. 快速体验（5 步）

1. **看**：首页点「出品中の作品を見る」→ 点任意作品 → 看右栏的**竞价台账**（当前价、剩余时间、出价历史）。
2. **拍**：用 `demo@hew.local` 登录 → 在作品页输入金额 → 「この金額で入札する」。
   再打开另一个浏览器窗口用 `artist1@hew.local` 登录去加价，就能看到**自动入札**（上限内自动加价 10 pt）和
   **前一位最高价的退还**。
3. **画**：`絵を描く` → 选 10 秒 / 30 秒 / 1 分 / 5 分 → 「描き始める」→ 用鼠标或触摸画 → 「完成する（PNGで保存）」。
   倒计时结束后会自动停止并冻结画面（保存后不能再添笔）。
4. **出品**：保存对话框里点「出品設定へ進む」→ 填标题 / 说明 / 标签 / 起拍价 / 结束时间
   （有「デモ: 2分後」预设，方便看结束流程）→ 确认对话框 → 公开，拍卖立即开始。
5. **算账**：`アカウント` 看余额、下書き、出品中、两类收藏；`通知` 看应用内通知与**邮件队列**；
   `ボーナス` 领注册 500 / 初次作画 50 / 初次出品 100 pt。

### 做进业务规则里的（不只是画面）

- 入札条件：举办中 / 未过结束时间 / **禁止自己投标** / 高于当前价 / 余额够。
- 受理时**立即扣点**，被超越时**退还前一位最高价**（余额、投标历史、点数交易、当前价、通知同一批处理）。
- 自动入札：他人出价时在上限内加价；**上限相同则设定时间早的人优先**（这一点有自动测试覆盖）。
- 结束：只能由**结束时间**触发（到点后的入札一律拒收）；落札时**不重复扣款**；无人出价则落札者なし。
- 下書き**只有作者可见**，保存后无添笔入口，编辑的只有出品信息。
- 秒级刷新只改写「活着的数字」（剩余时间、进度条），不会破坏正在输入的入札表单。

## 3. 明确没做的（边界）

- **没有服务器 / 数据库 / Flask**：全部在浏览器内，数据在 `localStorage`。
- **没有真正的认证**：密码只是混淆保存，不是哈希；没有 CSRF / 排他锁。不要当安全实现使用。
- **没有 Stripe**：无支付通信、无加点（与要件 5.7 一致）。
- **没有 SMTP**：通知只写进「未送信」的队列记录，不发送。
- **没有后台管理、直播、NFT、取消、再出品、吊り上げ bot**（要件 6 的対象外）。
- 客户端画的 PNG **无法证明没有被篡改**（与要件 9 章的已知限制一致）。

## 4. 设计说明（为什么长这样）

主题是「**限时画出来的一张图，拿去竞价**」。所以设计语言取自这个题材自己的世界：
**印刷工房的目录**——套准标记（トンボ）、网点（halftone）、值札（值牌带穿绳孔）、判子（标签印章）、
以及数据一律用等宽字排成**台账**。作品卡片做成**带打孔和齿孔的票券**，因为它是可以被「撕下来买走」的东西。

- **颜色只有 5 种**：紙 `#EFEEE9`／墨 `#16181C`／藍 `#27407F`／蛍光紅 `#FF3D6E`／濃紅 `#B3123E`。
  其中**蛍光紅只用于「此刻还活着」的状态**——剩余时间、当前最高价、你自己的那一行、倒计时进度条。
  其余一切都是墨与藍。这样一眼就能看出「哪里正在动」。
- **字体三个角色**：New Tegomin（标题 / 作品名，有手写与版画味）＋
  Zen Kaku Gothic New（正文/UI）＋ IBM Plex Mono（金额、时刻、ID，tabular 数字对齐）。
- **签名元素**：倒计时不是数字，而是一道**会自己画过去的墨线**（hero 的横线、作品卡与详情页的进度条、
  作画画面顶部的计时条），最后 10 秒转为濃紅。它把「时间」这个题材变成版面上真正存在的东西。
- **文案**：全部日文、用动词、说清楚下一步。错误具体到数字（「ポイントが足りません。必要 1,200 pt / 使える 800 pt」），
  空状态是邀请而不是墓碑（「まだ出品された作品がありません。最初の一枚を描いて出品してみましょう。」）。
- **可达性**：跳转链接、可见焦点、表单 label、`aria-live` 的提示与倒计时、图片固定宽高比、
  `prefers-reduced-motion` 下关闭动画、URL 保存筛选状态、日本时间显示（`Intl` / Asia/Tokyo）。
- 截图见 `docs/`。

## 5. 未决事项的开发默认值

要件 9 章尚未决定的部分，为了让原型能跑，选择了下列临时值（都在代码里集中、可改）：

| 未决事项 | 本原型的临时实现 |
|---|---|
| 奖励点数量 | 注册 500 / 初次作画 50 / 初次出品 100 pt，每人每种 1 次，需要手动「受け取る」 |
| 图片尺寸上限 | PNG 4 MB 级、画布固定 1000×750（4:3） |
| 自动入札 | 每次加价 10 pt，达到上限即退出；上限相同按设定时间早者优先 |
| 最高价者再次出价 | 退还旧的最高价后再扣新价（净差）；余额检查会加回被冻结的旧价 |
| 落札后的交付 | 不向出品者转移点数、不转让图片所有权、不提供下载 |
| 无人出价结束 | 作品保持公开只读，Ver0.5 不提供再出品 |
| 邮箱所有权确认 | 未实现确认邮件，注册不代表邮箱已验证 |
| 通知 | 入札受理 / 最高价更新 / 落札 / 出品结束 / 自动入札设定 / 奖励；邮件只入队不发送 |

## 7. 开发与验证

```powershell
# 语法检查
node --check assets/js/store.js

# 单文件版（内联 CSS/JS）
node tools/bundle.mjs

# 用本地服务器打开（可选，file:// 也能用）
python -m http.server 8080
```

本原型在开发时用**无头 Chrome + CDP** 做过两轮自动验证：

- 业务规则约 70 项断言：注册/重复、密码规则、邮箱格式、下書き权限、发布校验（过去时间/无标签/负价/重复出品）、
  首次出价必须高于起拍价、自己不能投标、余额不足、退还、自动入札（含同额上限先设定者优先）、
  结束只处理一次、落札不重复扣款、奖励领取一次、标签 AND 检索、台账与余额一致、余额不为负。
- 真实 UI 操作：标签筛选写入 URL、排序、入札表单提交后的提示与价格更新、自动入札设定、
  在 Canvas 上真实拖动绘制→保存→生成下書き→出品→作品页、通知已读、奖励领取、登出后的权限收敛。

> 这些测试是开发期的一次性脚本，没有放进仓库。如需长期回归，可以按同样的方式用 CDP 重建。

## 8. 下一步：接到 Flask 上

1. `store.js` 里的每个方法都对应一个后端动作，函数名（`register` / `saveDraft` / `publish` / `placeBid` /
   `setAutoBid` / `closeExpired` / `claimBonus` / `toggleFav*`）可直接对应 Blueprint 的路由与 service 方法。
2. 把 `store.js` 的赋值换成 `fetch` 调用、把 `ui.js` 的渲染结果交给 Jinja 模板即可；CSS 与 Canvas 逻辑可原样使用。
3. 后端必须补上的东西：密码哈希（Werkzeug）、CSRF（Flask-WTF）、`SELECT ... FOR UPDATE` 行锁、
   UTC 保存 / 日本时间显示、每作品 1 场拍卖的唯一约束、以及 `bids.auction_id` 的 UNIQUE 约束**必须去掉**（要件 10 章）。
