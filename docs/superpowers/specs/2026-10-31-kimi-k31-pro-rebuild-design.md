# HEW2026 Kimi K3.1 Pro 独立重版设计

日期：2026-10-31

## 1. 目标

在仓库根目录新建 `HEW2026_v1.0_Chatbox_KimiK3.1Pro/`，以当前 `HEW2026_v1.0_MiniMaxCode_MiniMaxM3.1Flash/` 的 Ver0.5 功能与业务规则为基准，独立编写一套 Flask Web 系统，并采用已确认的「月白极简」视觉方向。

本版允许参考 MiniMax 版的需求、页面行为和验收标准，但不通过复制其源文件后改名的方式完成，也不恢复 Git 历史中的 Kimi 实现。MiniMax 版及仓库其他版本保持原状。

## 2. 功能范围

### 2.1 必须实现

- 用户名注册、登录、退出和恢复代码重设密码；不使用邮箱。
- 显示名编辑、恢复代码重新生成，以及账户内作品、收藏、自动入札和积分记录。
- 1024×1024 Canvas 限时绘画，提供 10 秒、30 秒、1 分钟和 5 分钟档位。
- 多图层、图层顺序／显示／不透明度、G 笔、圆笔、模糊、橡皮擦、Undo／Redo。
- IndexedDB 临时恢复，服务器绘画期限不因浏览器恢复而延长。
- 合成 PNG 和图层数据的正式保存、草稿访问控制和保存后不可再次加笔。
- 草稿出品并立即开始拍卖，设置标题、说明、既有标签、开始价格和结束时间。
- 商品详情内手动入札，采用输入、确认、确定流程；支持自动入札。
- 入札扣点、前一最高入札者退款、自己增额时只扣差额、残高与期限校验。
- 到期结束、落札者确定、出品者积分入账、通知以及重复执行防护。
- 注册、首次出品和绘画奖励；奖励规则可配置，默认值与 MiniMax 版一致。
- 关键词搜索、多个标签 AND 搜索、作品与拍卖分开收藏。
- 应用内通知、通知已读、奖励页面、积分记录。
- 充值和支付仅提供说明页面，不连接真实支付服务，不变更余额。
- 日语界面、桌面与手机响应式布局。

### 2.2 明确不实现

- 制作直播、直播评论和评论审计。
- 管理后台。
- 拍卖取消与再出品。
- 真实充值、支付或外部结算。
- 邮件发送。
- 正式 WebRTC、摄像头、麦克风或录制功能。

## 3. 视觉与交互设计

### 3.1 设计方向

采用「月白极简」：暖白与浅灰背景、近黑正文、蓝紫强调色、较大的留白、圆角作品卡和轻量边框。作品图片是首页与详情页的主要视觉焦点，装饰性渐变只用于少量品牌元素，不干扰阅读。

界面文字使用日语。正文字体优先系统无衬线字体，标题使用较高字重和紧凑字距。颜色不能作为状态的唯一表达方式，进行中、已结束、草稿等状态同时提供文字。

### 3.2 页面原则

- 首页：品牌导航、简洁主视觉、公开作品和进行中拍卖；移动端将导航折叠为可操作的菜单。
- 商品详情：作品图、当前价格、剩余时间和入札操作形成第一视觉层级；历史、收藏和自动入札位于其后。
- 绘画页：画布优先，工具与图层围绕画布组织；窄屏使用可展开工具面板，不缩小到难以操作。
- 出品、登录、注册和账户表单：明确标签、必填项、错误位置和提交状态。
- 所有交互按钮具备 hover、focus、disabled 状态；键盘焦点清晰可见。

## 4. 技术架构

### 4.1 技术栈

- Python 3.13、Flask、Flask-SQLAlchemy、Flask-Migrate。
- Flask-Login、Werkzeug 密码哈希、Flask-WTF 与 CSRF 保护。
- Jinja2 模板、原生 CSS、原生 JavaScript、Canvas 与 IndexedDB。
- MySQL 8／MariaDB（utf8mb4）为主要运行数据库；SQLite 仅用于开发和自动化测试。

### 4.2 模块边界

采用 Application Factory 与 Blueprint，按以下职责组织：

- `auth`：注册、登录、退出、恢复代码。
- `artworks`：绘画会话、正式保存、图像访问、出品设置。
- `auctions`：详情、手动入札、自动入札、结束处理入口。
- `account`：账户资料和用户相关列表。
- `search`：关键词与标签搜索。
- `favorites`：作品与拍卖收藏。
- `notifications`：通知列表与已读。
- `points`：奖励、积分流水、充值与支付说明。
- `main`：首页和公共资源。
- `services`：认证、图片、图层、作品、拍卖、积分、标签和通知业务规则。
- `models`：持久化模型，不在模型中堆放路由或模板逻辑。
- `templates` 与 `static`：页面、样式、Canvas 和详情页交互。

路由负责输入输出与权限入口，服务层负责事务和业务不变量，模型负责数据结构。绘画浏览器端只负责交互和临时恢复，期限、权限和文件有效性最终以服务端为准。

### 4.3 数据模型

核心实体包括用户、作品、绘画会话、拍卖、入札、自动入札、标签、作品标签、两类收藏、钱包流水、通知和奖励记录。

- 用户名唯一，密码与恢复代码只保存哈希。
- 一幅作品最多一个拍卖，入札历史允许同一拍卖对应多条记录。
- 钱包流水保存业务类型、金额和关联对象，结束结算具有防重复依据。
- 时间统一以 UTC 保存，显示时转换为 Asia/Tokyo。
- 图片与图层 ZIP 保存在静态公开目录之外，通过带权限检查的路由读取。

## 5. 核心业务流程

### 5.1 绘画与出品

1. 登录用户选择绘画时长，服务器创建带固定期限的绘画会话。
2. 浏览器绘制并写入 IndexedDB；恢复只还原内容，不延长服务器期限。
3. 正式保存时上传合成 PNG 与图层数据，服务端校验签名、尺寸、层数、单文件和总容量。
4. 保存成功后形成草稿并发放符合条件的绘画奖励，浏览器临时数据可以清理。
5. 作者填写出品信息，服务端再次校验所有权、图片、价格与期限。
6. 出品与拍卖开始在同一事务中完成，并按规则发放首次出品奖励。

### 5.2 手动与自动入札

1. 用户输入金额后进入确认步骤，确定时重新检查拍卖状态和当前价格。
2. 服务层在单个事务中锁定相关拍卖、入札者和前一最高入札者记录。
3. 校验自己入札、结束时间、最低增幅、余额与确认时价格。
4. 扣除实际所需积分，记录入札和钱包流水，返还被超越者未返还金额，更新当前价格。
5. 自动入札按上限和余额计算必要的最小增幅；同额上限由设置时间较早者优先。
6. 自动入札余额不足时，本次不再加价，停止该设置并通知本人。
7. 价格被其他请求改变时，确认请求失败并要求用户重新确认，不覆盖新价格。

### 5.3 到期结束

`close-auctions` CLI 批次处理已到期拍卖。服务层确定落札者与最终价格，向出品者入账并生成通知。重复执行不得重复扣款、退款、入账或通知。无入札拍卖按 Ver0.5 规则结束且不提供再出品流程。

## 6. 默认业务参数

与 MiniMax 版默认行为保持一致，并允许通过环境变量调整：

- 注册奖励 1,000 pt，仅一次。
- 首次出品奖励 300 pt，仅一次。
- 绘画奖励 100 pt，每个 JST 自然日最多一次。
- 最小加价幅度 1 pt。
- 合成 PNG 不超过 5 MiB，每个图层 PNG 不超过 5 MiB，展开后总计不超过 50 MiB。
- 正式保存重试宽限期 60 秒。
- `reserve_price` 不参与落札判断。
- 开发环境可使用 SQLite；生产环境必须显式配置安全密钥和数据库。

## 7. 安全与异常处理

- 所有 POST 请求启用 CSRF，认证和所有者权限在服务端检查。
- 不提交 `.env`、真实密码、数据库连接密码或密钥。
- 上传文件验证真实结构，不信任扩展名、浏览器 MIME 或客户端声明。
- 草稿、原始图片和图层 ZIP 按权限访问，不通过猜测静态 URL 公开。
- 表单错误保留用户输入并给出可理解的日语提示。
- 提供统一 403、404、500 页面；服务器错误记录日志，但不向用户泄露堆栈或连接信息。
- 数据库异常时回滚整个业务事务，不出现只扣款不入札等部分成功状态。

## 8. 运行与预览

项目提供 `.env.example`、依赖清单、初始化命令和 README。开发启动支持：

- `python main.py`。
- `npm run dev`，并将 `--host`、`--port` 参数转发给 Flask 启动入口。

数据库初始化、标签种子数据、演示数据和拍卖结束命令分别提供，不让测试操作依赖开发数据库。
